# LiveBook AI 改造设计：实时成交记录引擎

**版本：v0.1（设计稿）**
**日期：2026-08-17**
**状态：待评审**

---

## 0. 背景与问题

### 0.1 真正的目标

把 `speech2text` 工程中已验证过的两套**成交记录自动分析方案**，移植成 LiveBook AI（macOS App）内的**实时方案**：

> **直播进行中（无需任何文件输入）：**
> **实时捕获直播窗口画面（ScreenCaptureKit）+ 实时捕获系统音频（流式 ASR）+ 实时 OCR 识别屏幕上的弹幕栏 → 融合 → 实时生成成交记录（书名、买家、成交价、出价阶梯、时间窗口、状态）**

### 0.1.1 关键前提：实时 ≠ 事后文件

- **视频文件（回放 mp4）**：直播结束后才有 → 实时路径**不能**依赖它；
- **弹幕文件（平台导出 JSON）**：直播结束后才有 → 实时弹幕**必须**从屏幕上 OCR，而不是读导出文件；
- 回放文件 + 导出弹幕 **仅用于开发调试与校准**（当前唯一数据源是 0813 回放），产品形态以**实时直播模式**为唯一主路径。

### 0.2 当前工程为何"不对"

当前 LiveBook AI 大量代码投入在 OCR / ISBN / 最佳画面 / 基准校验（对应 `LIVEBOOK_AI_MACOS_SPEC.md` 的 Phase 1），而**核心链路（实时成交记录）恰恰最弱**：

- `LiveAuctionParser` 只识别「恭喜X老师」一种成交信号，且无买家别名、中文价格词典；
- 弹幕栏 OCR 只做文字收集（`danmakuLines`），**没有解析成出价阶梯**；
- 没有"成交时刻 → 最近封面 → 书名"的对齐逻辑；
- `AuctionRecord` 模型没有 bids 阶梯 / 时间窗口 / 封面 / 状态，无法对账。

### 0.3 本设计的范围

只做实时成交记录引擎；OCR/捕获/ASR 基础设施全部复用；ISBN/最佳画面降级为辅助能力（仍可用于封面识别与书名候选）。

## 1. 方案来源（speech2text 已验证的资产）

### 1.1 方案 A：音频成交信号（`fusion_pipeline_v7.py`，0807–0813）

流程：sherpa ASR 时间戳转写 → 扫描结拍信号 → 信号前取最近价格+买家 → DB 监督过滤 → OCR 封面对齐。

成绩：42 条成交事件，DB 44 条覆盖 40/44 = 91%，并纠正 DB 中 2 处价格错、2 处买家错。

**必须移植的信号与词典：**

| 资产 | 内容 |
|---|---|
| 结拍谐音信号集 | `{结拍, 节拍, 接拍, 截拍, 解拍}` |
| 倒计时信号 | `[五无]四三二一` |
| 恭喜信号 | `恭喜<买家>` |
| 中文价格词典 | `一百五=150, 两百六=260, 七十五=75, 一千=1000, ...`（约 40 项）+ 数字正则（30–2000） |
| 买家别名词典 | ASR 误识别映射（示例：`买家甲→[甲老师,甲先生,...]`、`梅先生→[明老师,明明,...]` 等），真实名单不入仓库 |
| 去重规则 | 时间差 <30s 且 买家+价格 相同 → 一次 |

### 1.2 方案 B：弹幕出价（0816 实践）

弹幕窗口内容**即出价**：

- 出价行：`"买家甲 5"`、`"买家乙 10"`（弹幕栏内「发送者 + 数字」）；
- 分隔线：`"-------------"`（`作者 | -------------`）= **成交边界**；
- 窗口（两条分隔线之间）内收集**出价阶梯** `bids: [[出价人, 价格], ...]`，最后一条 = 买家 + 成交价。

产出：`danmu_0816_records.json`（22 条，含 `window_sec` + `bids`），并人工核对书名生成 `0816.csv`（书名,买家,成交价）。

### 1.3 关键认识

- 弹幕是**精确文本**（平台用户名，无 ASR 误识别），但**只给出价，不给出成交语义**；
- 音频 ASR 是**模糊文本**（有误识别），但**提供成交语义**（结拍/倒计时/恭喜/流拍）；
- 两者互补：**弹幕定"谁出到多少钱"，音频定"这一单何时结束"**；封面 OCR 定"卖的是哪本书"。

## 2. 目标架构

```
┌─ 实时直播模式（主路径，直播进行中）───────────────────────────────┐
│  ScreenCaptureKit 捕获直播窗口                                      │
│   ├─► 封面区 OCR ──────► 书名/ISBN 候选（每窗口对齐）              │
│   ├─► 弹幕区 OCR ──────► 弹幕出价解析器（bids 阶梯 + 分隔线边界）    │
│   └─► 系统音频 ──► sherpa 流式 ASR ──► 成交信号检测器               │
│                                          ▼                          │
│                                 AuctionFuser（状态机）              │
│                                          ▼                          │
│                     AuctionRecord ──► 实时记录列表 + 导出           │
└──────────────────────────────────────────────────────────────────────┘

┌─ 回放调试模式（仅开发/校准用，产品不依赖）──────────────────────────┐
│  ReplayFileSource（0813 回放）走同一管线，用于：                     │
│   · 弹幕行格式/区域校准    · 信号词典回归验证    · 端到端对账        │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.1 模块划分（全部 UI 无关、可单测，参照现有 `ValidationRunner` 模式）

| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| `DanmakuBidParser` | 弹幕行 → 出价阶梯；分隔线边界 | OCR observations（弹幕区） | 当前窗口 bids、边界事件 |
| `SettlementSignalDetector` | ASR 文本 → 成交/流拍信号 | 流式转写文本 | 信号事件（含时刻、买家/价格提取） |
| `AuctionFuser` | 状态机：聚合以上 + 封面 | 各事件流 | `AuctionRecord` |
| `CoverAligner` | 窗口内封面候选 → 书名 | 封面区 OCR 观察 | 书名候选（窗口对齐） |

### 2.2 数据流时序（一单的完整生命周期）

```
INTRODUCING    封面 OCR 出现书名候选（窗口开始）
  │
BIDDING        弹幕出价阶梯累积；音频可确认当前价
  │
SETTLED        音频"结拍/倒计时+恭喜" 或 弹幕分隔线触发
  │             → buyer = 阶梯最后一条的出价人（音频兜底）
  │             → price = 阶梯最后价格（音频兜底）
  │             → book  = 窗口内最近封面候选
  │             → 封面图 = 窗口内最佳帧
  ▼
AuctionRecord 加入列表 + 导出
（PASSED：音频"流了/没人要/下一本"或窗口内零出价）
```

## 3. 模块详细设计

### 3.1 弹幕区识别（DanmakuRegion）

现状：硬编码右栏 `maxX > 0.72`（`LiveAuctionParser.ingestOCR`）。

设计：
- 默认区域：右侧竖栏 `x ∈ [0.72, 1.0]`（可配置），保留 Vision 归一化坐标；
- 支持配置项 `danmakuRegion`（UI 可拖框校准，存 `UserDefaults`）；
- **校准步骤（R1 验收）**：用 0813 回放的实际弹幕栏帧确认屏幕上的弹幕行格式（`发送者+数字` 的具体排版），据此定正则；
- 弹幕区与封面区（`coverRect`）重叠部分以弹幕区优先（避免出价数字混入封面候选）。

**实时读取的固有挑战（直播中弹幕是滚动的）：**
1. **滚动丢行**：弹幕行持续滚动，2 FPS 采样可能漏掉快速滚过的出价行 → 弹幕区单独提高采样（如 5 FPS 仅裁弹幕条），并在 `AdaptiveFrameSampler` 之外对弹幕区做独立降采样 OCR（弹幕区小，OCR 成本低）；
2. **滚动模糊**：滚动中文字可能被 OCR 读成乱码 → 弹幕区 OCR 用 `.accurate`；同一出价行若连续 2 帧都读到**同价格**，取置信度高者；
3. **出价数字在滚动中短暂可见**：价格行平均可见时长决定可读性——若实测命中率不足，增加"连续 N 帧去重合并"策略；
4. **发送者与数字分行**：滚动弹幕常把「发送者」和「数字」拆成两行 → 按时间顺序维护"最近发言者"，纯数字行归属最近发言者（见 3.2 规则 3）；
5. **礼物/系统消息干扰**：`送礼物`、`进入直播间` 等行过滤（关键词黑名单）。

### 3.2 弹幕出价解析器（DanmakuBidParser）

输入：弹幕区的 OCR observation（text + boundingBox + timestamp）。
处理（每行）：

1. **归一化**：去空白/标点（复用 `TitleMatcher.normalize`），保留数字与汉字；
2. **分隔线检测**：行内容为纯 `-`/`＝`/`=`
（≥4 个连续分隔符）→ 触发**窗口结算**（见 3.5），并开启新窗口；
3. **出价解析**（按优先级）：
   - `发送者 + 数字`：`^(.*?)[:：\s]*(\d{1,4}|[零一二三四五六七八九十百]+)\s*(元|块)?$`，发送者与数字间有分隔；
   - `纯数字`（如 `"5"`）：价格归入**最近发言者**（弹幕按时间顺序，发送者行与数字行相邻）；
   - `发送者出价N元` 等口语形式（正则兜底）；
   - 无法解析的普通弹幕 → 丢弃（不计入阶梯）；
4. **买家名匹配**：弹幕用户名是精确文本 → 直接匹配已知买家集合（`knownBuyers`，可配置/自动积累）；未知名保留原样；
5. **阶梯更新**：价格**单调递增**校验（同窗口内后价 ≥ 前价才入阶；异常价标记 `NEEDS_REVIEW`）；
6. **去重**：同窗口内同发送者同价格不重复入阶。

输出：`struct DanmakuBid { sender, price, t }`；当前窗口 `bids: [DanmakuBid]`；边界事件 `onWindowClose`。

### 3.3 成交信号检测器（SettlementSignalDetector）

输入：sherpa 流式转写的增量文本（`LiveTranscriber.feed` 返回值）。
处理（窗口滚动，参照 `fusion_pipeline_v7._extract_at`）：

1. **信号集合**：
   - 成交：`结拍|节拍|接拍|截拍|解拍`、`[五无]四三二一`、`恭喜(?:我们)?买家(?:老师)?`；
   - 流拍：`没人要|流了|流标|没人拍|下一本|撤拍`（规格 §17）；
2. **价格提取**：中文价格词典（移植 `PRICE_CN`）+ 数字正则（30–2000），取信号前最近价格；
3. **买家提取**：买家别名词典（移植 `BUYERS`），优先级：`恭喜` 后 20 字内 → 价格前 35 字内 → 信号前 60 字内；
4. **去重**：同信号位置只触发一次（记录偏移，参照现有 `settledOffsets`）。

输出：`enum SettlementSignal { sold(buyer?, price?), passed }` 事件。

### 3.4 封面对齐（CoverAligner）

- 窗口开启后，持续收集封面区 OCR 候选（去重、保置信度）；
- 结算时：取窗口内**最近出现**的候选为书名（`nearest_cover` 语义：成交前最近封面），并附上窗口内**最佳帧**（复用 `BestFrameSelector` 或直接取结算时刻最近帧）；
- ISBN（如有）一并附到记录。

### 3.5 实时融合器（AuctionFuser，状态机）

```
IDLE ──封面候选/出价──► INTRODUCING ──► BIDDING ──成交信号或弹幕分隔线──► SETTLED ──► 记录
                              └────────流拍信号 / 窗口超时 / 零出价────────► PASSED
                              └──────────── 异常 ────────────────────────► NEEDS_REVIEW
```

- 状态机纯逻辑、线程安全（事件从 OCR 队列/音频队列并发进入，内部串行化——参照现有 `LiveAuctionParser` 的 lock + snapshot 模式）；
- **结算字段优先级**：
  - buyer/price：弹幕阶梯最后一条（**主**）→ 音频信号提取（**兜底**）；
  - book：封面对齐（**主**）→ 音频推断书名（`inferTitle`，现有）→ `（待识别）`；
  - 状态：音频成交信号 → SOLD；流拍信号或零出价 → PASSED；buyer 或 price 缺失 → NEEDS_REVIEW；
- **去重**：同 buyer+price 且窗口起止接近（<30s）→ 合并；
- **来源标记**：`source: danmaku / audio / both`，用于离线对账。

### 3.6 记录模型升级（AuctionRecord v2）

```swift
struct AuctionRecord: Identifiable, Codable, Sendable {
    let id: UUID
    var no: Int                      // 本场序号
    var bookTitle: String
    var isbn: String?
    var buyer: String?
    var price: Int?
    var bids: [DanmakuBid]           // 出价阶梯（方案 B 核心输出）
    var windowStart: Double          // 窗口起
    var windowEnd: Double            // 窗口止（结算时刻）
    var coverImagePath: String?      // 封面图（持久化）
    var status: AuctionStatus        // SOLD / PASSED / NEEDS_REVIEW
    var source: String               // "danmaku" / "audio" / "both"
    var confidence: Double
}
```

导出格式对齐 `danmu_0816_records.json`：
```json
{ "no": 1, "window_sec": [0, 663], "buyer": "买家乙", "price": 40,
  "bids": [["买家甲", 5], ["买家乙", 10], ...], "book": "书名…", "status": "SOLD" }
```
（CSV：`书名,买家,成交价`，带 BOM，与 0808–0816.csv 一致。）

## 4. 实施步骤（含验收标准）

> 说明：所有模块先用 **0813 回放调试模式**开发与校准（当前唯一数据源），但每个模块的接口都是**实时事件驱动**的，接入实时直播模式（ScreenCaptureKit）零改动——与现有 FrameSource 抽象同理。

### R1：弹幕出价解析器（DanmakuBidParser + 区域识别）
- 用 0813 回放校准弹幕行格式（滚动排版、发送者+数字格式）；实现解析器 + 分隔线检测 + 阶梯状态 + 滚动丢行合并策略；
- 单测：构造弹幕 observation 序列 → 阶梯正确、边界正确、单调校验、去重、丢行合并；
- **验收**：对 0813 回放弹幕区跑 OCR，阶梯结构可与人工核对，出价行捕获率（相对人工清点）≥ 70%。

### R2：成交信号检测器（SettlementSignalDetector）
- 移植 结拍谐音集 / 倒计时 / 恭喜 / 流拍 + 价格词典 + 买家别名词典；
- 单测：用 0813 ASR 转写（`/tmp/0813_transcript.json` 已有数据）回放 → 信号时刻与 `sales_0813_timed.json` 的 t_sec 对齐；
- **验收**：信号检测命中率 ≥ 85%。

### R3：融合器 + 记录模型（AuctionFuser + AuctionRecord v2 + CoverAligner）
- 状态机、字段合并优先级、去重、封面对齐、记录持久化；
- 单测：模拟三路事件流 → 记录字段正确；
- **验收**：对 0813 回放端到端跑一遍，输出记录与 `0813.csv`（或 `all_records_verified.json` 语义）对账，命中率 ≥ 80%。

### R4：实时直播模式打通（核心！产品主路径）
- 把 R1–R3 的管线接到 `ScreenCaptureManager`（视频 + 音频 + 弹幕区 OCR 全部来自直播窗口）；
- 直播中**每单结算即出记录**（实时列表刷新 + 自动导出 JSON/CSV 到会话目录）；
- **验收**：开启一场真实直播（或对着直播窗口），弹幕出价 → 成交信号 → 记录实时生成，端到端可用（需屏幕录制权限；首次用真实直播窗口人工核对 3–5 单）。

### R5：UI 完善 + 导出 + 对账
- 实时记录列表、bids 展开、封面缩略图、状态徽标；CSV/JSON 导出（格式与 0816 一致）；
- 直播结束后的**离线对账**：用回放/导出弹幕重跑同一管线，与实时记录比对（ValidationRunner 扩展）；
- **验收**：回放模式端到端导出文件与 0816 格式一致；实时/回放两路结果可对账。

### R6（后续可选）：DB 监督 / 二次销售草稿 / 打印
- 实时无 DB 时用"阶梯合法性"替代监督过滤；接入 Book Matrix 后启用监督。

## 5. 关键决策点与风险

| # | 决策点 | 建议 | 依据 |
|---|---|---|---|
| 1 | 弹幕来源 | **屏幕 OCR**（不做平台接口/逆向；弹幕文件仅离线校准用） | 规格 §2 铁律；弹幕文件直播后才存在 |
| 2 | 弹幕行格式 | R1 用 0813 回放帧校准（`recognitionLevel = .accurate`） | 0813 回放实测 |
| 3 | buyer/price 主源 | 弹幕阶梯为主、音频兜底 | 弹幕精确、音频有语义 |
| 4 | 成交边界 | 音频信号优先、弹幕分隔线次之（谁先触发谁结算） | 两方案均已验证 |
| 5 | 性能 | 弹幕区独立降采样 OCR（弹幕条小，成本低）；ASR 已在流式 | 实时滚动弹幕需更高采样 |
| 6 | 风险：滚动弹幕丢行 | 弹幕区 5 FPS 采样 + 连续帧去重合并 + 丢行容错 | 见 §3.1 实时挑战 |
| 7 | 风险：弹幕栏被主播/礼物覆盖 | 区域可配置 + NEEDS_REVIEW 兜底 | — |
| 8 | 风险：同买家多单连拍 | 分隔线/信号窗口隔离 + 序号递增 | 0816 记录含 window 字段 |
